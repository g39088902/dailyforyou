核对结论

不是"接口不够多"，而是三份事实仍然各说各话：契约设计完整，实现停在 P0 之前。

01

P0 三个端点全部未落地 P0

/sources、/logo/:file、/health 在 backend/src 中 grep 不到任何注册；crawler 侧也只有 news_items 与迁移账本，sources / source_logos 两张表尚未创建。契约 README 的"发布顺序"一步都还没走。

02

前端仍是"四份清单"原状 P1

store/index.js 27 条 defaultNewsArr、api/index.js 的 5 个前缀白名单、public/logo/ 32 张 png、4 处 /logo/{name}.png 直取——与 contracts/frontend.md §2 的删除清单逐条对应，一处都没动。这是 /sources 缺失的连带结果，不是独立欠账。

03

沉默失败仍未消除 P0

未知信源仍返回 200 + data: []（newsDb.ts:147 兜底 meta），前端无法区分"暂无数据"与"信源不存在"；不可用的 GET /all 已于 2026-10-21 删除，deploy.sh 改为探测单信源 200，但爬虫停摆依旧无法从健康检查看出来。

04

一条"已封装、未接线"的前端能力 P1

getScoreRecords（api/index.js:109）有封装但零调用方，人工校准样本的查询能力闲置。登录侧的 getAuthMe 与后端 /auth/me 已于 2026-10-21 一并移除——登录态仍完全由 localStorage 决定，token 过期要等业务请求 401 才清理。

05

鉴权边界是清晰的 OK

/score 与 /score/* 的两条 requireAuth 注册在所有处理器之前，实测 /api/score 返回 401；/account/* 同样锁定。资讯与登录前链路公开，符合契约。风险集中在"未实现"而非"漏鉴权"。

06

兼容别名可收敛 P2

手动评分有 6 个入口（POST|PUT|PATCH /score/manual、POST /score/feedback、PUT|PATCH /score），已读有 3 个，评分记录查询有 3 个；前端每个只用其中一个。别名层在灰度期有价值，稳定后可只保留规范路径。

核对口径
  • 后端：全量扫描 backend/src 的 Hono 注册点（registry.ts、routes/news.ts、auth/index.ts、api/account.ts），按逻辑端点归并，别名在行内注明。
  • 前端：frontend/src/api/index.js（7 个封装）+ api/auth.js（9 个封装）逐一 grep 调用方，覆盖 .vue 与 composables。
  • 规划：docs/contracts/backend.md §2–§6、docs/contracts/README.md §7 分期表；仅统计有明确请求/响应定义的接口，不含内部函数契约。
  • 爬虫：crawler/src 无 HTTP 服务端代码，对外端点 0 个，因此不参与接口统计；它只以 news_items 写库与后端集成。
